Why B Doesn't Break: Lessons from 10 Common Dev Mistakes

Hey everyone! Welcome back. When we first sat down to start designing B, we knew we had a massive mountain to climb. Making a multiplayer game entirely from scratch is a wild learning experience, and honestly, it's really easy to fall into traps that'll completely break your project later down the line.

Instead of grabbing a pre-made engine off the shelf, we decided to take the hard road. But not to worry, good things cost effort! We wanted to build our own custom engine using Three.js for the frontend graphics and Node.js for the server backend. It was a ton of extra work up front, but it gave us total control over exactly how the game runs.

Because of that choice, we've been able to build our world the right way from the ground up. When possible, we always chose to avoid the "Let's just put a placeholder here to add functionality... Later." motives that made development feel faster. This helped us dodge a lot of the classic headaches that usually haunt indie devs. In this blog, I want to dive into 10 big mistakes we've learned to avoid, and exactly how our custom engine keeps B running smoothly!

01

Blindly Trusting Tutorials

It's super tempting to find a tutorial on YouTube and just copy-paste the code to get something working fast. But if you don't really get *why* it works, you're gonna have a bad time later when it breaks and you have no idea how to fix it.

For B, we couldn't really do that anyway. We use a custom Z-up world where every block is 32 units tall. Most tutorials are for different kinds of games. So, we had to write all the important math for our Three.js engine ourselves. It was harder at first, but now we know exactly how every piece of our game works.

02

Position vs. Offset

This one is tricky. There's a big difference between a character's *real* spot in the world and where the art is drawn. If you move the art, that's just an offset. If you move the position, you're moving the hitboxes and where the game thinks you are.

In B, we keep these totally separate. Our Node.js server knows your exact grid position - that's the truth. Your game client just worries about drawing the art. That's how we can do cool effects like Spherical Billboarding, where your sprite tilts with the camera. The art moves, but your hitbox on the server stays perfectly flat on the ground.

03

Adding a God Mode

Testing a big game is a pain if you have to play it normally every time. You need a "god mode" to get around fast. That's why we built our own Developer Tools UI right into the game.

We can fly, teleport by clicking the map, place huge groups of blocks at once, and change game settings on the fly. It makes testing a million times easier. And don't worry, we made sure the server checks if you're an admin before it lets you do any of this, so there's no cheating for regular players.

04

Flipping Physics by Scaling

Here's a classic mistake: to make a character face the other way, some people just set their scale to -1. It looks right, but it secretly breaks all the physics and hitboxes attached to that character.

Think of it this way: children typically inherit traits from their parents, and it's the exact same with tables, objects, and web elements. When a parent passes down a scale of -1, the child inherits that flip and works completely normally. But if that child goes into its own negative range outside of our predicted paths, the numbers compound. You end up multiplying a negative by a negative, which... as we know... turns into a positive! That sudden flip is what breaks the vectors and distorts the hitboxes.

We're totally safe from this in B. Our server handles all the important stuff like combat, collisions, and where you're aiming. Your game client is just for show. So if you flip your sprite on the screen, the server doesn't even know or care. The real hitboxes are still in the right place.

05

Preloading and Memory Leaks

If you try to load a whole giant map into memory at once, your computer's going to overload and the game will crash. This is called a memory leak.

We fixed this in two ways; First, we use a texture atlas, which is one giant image with all our block textures on it. The game only has to load one file instead of hundreds! Second, we use chunk loading. The server only sends you the parts of the map that are close to you. When you walk away, your browser automatically dumps the old chunks it doesn't need anymore. This keeps the game's memory use super low.

06

Placing Enemies Directly in the Level

It's a waste of power to have an enemy on the other side of the map thinking about what to do when there are no players around. In a lot of games, all enemies are "on" all the time.

In B, our Node.js server is smart about this. It knows where players are. If a map chunk is empty, the server just lets the enemies in that area chill out. It doesn't waste time running their AI. This helps the server stay fast, which is super important when you have a lot of players fighting at once.

07

Resolution and Camera Scaling

Pixel art can look really bad if it's stretched on a weird-sized monitor. It gets all blurry or distorted. We knew this would be a problem, so we built our UI to be super flexible.

You can scale the whole interface up or down to fit your screen. We also made the zoom independent. You can zoom your main camera in for combat, but keep your minimap zoomed way out to see the whole area. Our WebGL canvas handles all this without making the art look ugly.

08

Static Typing vs Server Authority

Some coding languages are very strict. You have to tell them "this variable is a number" or "this is text". This is called static typing. It helps catch bugs. We use JavaScript, which is... not strict at all. You can put anything anywhere.

To stop people from cheating, our server acts like a bouncer. It checks everything. If you try to attack someone, the server makes sure you're sending a real damage number, not some text like "a million damage". The server enforces the rules so the game stays fair.

09

Version Control Resilience

This one is maybe the most important lesson for any dev. Use Git! It's like having a time machine for your code.

We've made some huge changes to B, like rewriting the whole graphics pipeline with InstancedMesh or moving all the combat to the server. Sometimes, those big changes break *everything*. With Git, if we mess up badly, we can just hit a button and go back to the last version that worked. It has saved us so many times.

10

FPS Limits and Hardware Toggles

If a game runs too fast, it can literally make your computer overheat. You need ways to control performance. We added a bunch of options for this in B. If your computer is struggling, you can turn off fancy stuff like shadows.

We also use a trick called face culling. The engine is smart enough to not draw the sides of blocks that you can't see (like a side that's touching another block). This saves a ton of power and helps keep the FPS smooth, even on older computers.

A Strong Foundation Matters

So yeah, building a game from the ground up is a wild ride. But by thinking about these common problems from the start, we built a really strong foundation for B. It's more stable, more secure, and easier for us to add cool new stuff without breaking the old stuff.
